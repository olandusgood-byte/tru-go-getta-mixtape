# TRU GO GETTA Game V1.4 Expansion Plan

## Baseline

- Stable branch: `game/v1-2-build`
- V1.3 City Jobs economy routing is merged and post-merge CI is green.
- Production remains gated.
- V1.4 work must be additive and must not replace or duplicate existing V1.3 systems.

## Goal

Turn the V1.3 systems into a more connected career loop without destabilizing the playable foundation.

## Proposed V1.4 scope

### 1. Career depth
- Connect career milestones to existing progression and district systems.
- Make existing recording, mixtape, and studio progression visibly affect the player journey.
- Preserve current career save compatibility.

### 2. Inventory-driven gameplay
- Give existing inventory items meaningful use in selected missions/activities.
- Keep item handling deterministic and save-safe.
- Do not create a second inventory system.

### 3. Crew progression
- Extend the existing crew system with progression hooks rather than replacing crew bonuses.
- Keep reward bonuses routed through the existing economy layer.
- Prevent duplicate reward application.

### 4. City life
- Deepen existing districts and repeatable events using the current district/event APIs.
- Prefer additional activities and stateful outcomes over new parallel navigation systems.

### 5. Player feedback
- Improve visible status for cash, XP, reputation, crew, inventory, districts, and achievements.
- Keep mobile controls usable.

### 6. Regression gate
V1.4 must preserve the V1.3 loop:

CREATE PLAYER → ENTER CITY → MOVE → TAKE MISSION → COMPLETE → CASH/XP → LEVEL UP → SAVE → LOAD

Required checks:
- existing V1.3 APIs remain available
- existing save keys remain compatible
- no duplicate DOM control IDs
- no duplicate reward paths
- mission chains still complete correctly
- district locks still work
- inventory, crew, events, and economy remain persistent
- browser smoke remains green

## Build order

1. Read-only audit of current V1.3 APIs and UI connections.
2. Select one small V1.4 vertical slice.
3. Build it on a dedicated feature branch from the current stable checkpoint.
4. Add deterministic browser coverage before merging.
5. Run the full static/browser gate.
6. Merge only after the feature branch is green.
7. Keep production gated.

## Explicit exclusions

- No production deployment.
- No force push.
- No destructive migration.
- No replacement of working V1.3 systems.
- No duplicate V1.2/V1.3 branch creation.
- No automatic release to production.
